# 智能体与真实仪器

AI4Instruments · 协议、接口与开源工程研究 · 2026-10-20

## 01 · 应该建设什么

值得建设的共同基础，是让不同 Agent 能够发现设备、理解能力、提交实验、观察物理结果，并把这些经验带入下一次操作。接口的价值最终体现在可迁移的实验能力上：更换模型、设备型号或实验室之后，哪些过程仍可复用，哪些条件需要重新确认。

现有项目已覆盖多条可行路径：MCP 包装已有驱动，CLI 驱动本地执行服务，实验计划交给既有控制系统，GUI 操作现有仪器软件，以及机器人直接操作实验装置。它们可以共存。实验室通常已有一部分控制能力，先把这些能力描述准确，往往比从头重写设备接入更有价值。

协议设计的重点是连接“请求”与“物理事实”。服务器收到命令、设备接受设定、执行结束、达到实验目标，是四件不同的事。成功的传输只能证明其中一部分。

## 02 · 一条完整接入链的分工

| 层 | 负责什么 | 典型已有材料 |
| --- | --- | --- |
| **研究与推理** | 研究目标、下一步实验、结果解释、程序生成。 | Coscientist、AILA、SynAgent、量子校准 Agent。 |
| **Agent 接入** | 工具发现、调用、知识读取与结果返回。 | MCP、CLI、Python API、Skills。 |
| **仪器说明** | 能力、量纲、模式、状态、动作结果、任务与资源含义。 | SiLA 2、LADS、WoT、OpenMHP，以及 AIP / LAP 设计与 MHS 公开材料。 |
| **执行与编排** | 持有连接、运行长实验、协调设备、记录状态和结果。 | QCoDeS/Jupyter、Bluesky、Osprey、PUDA、Uni-Lab-OS、IvoryOS。 |
| **设备接入** | 把操作变为实际设备调用；处理型号和固件差异。 | SCPI/VISA、EPICS、TANGO、ROS、厂商 SDK、串口、GUI。 |
| **物理装置** | 运动、激励、采集、触发与真正的物理反馈。 | 仪器、控制器、传感器、样品和实验连接。 |

知识、控制和数据应分别组织。手册与 Skills 说明怎么用；控制接口提交操作并取得状态；大波形、图像和数据集由文件或数据服务传送，以引用和摘要进入 Agent 上下文。数据通道的选择由采样、吞吐和部署需求决定，Arrow Flight 并非每种仪器的必选项。

硬实时触发、伺服和采集时序由仪器、FPGA 或本地控制程序完成。Agent 选择目标和过程，并在有意义的时间点检查反馈。MHS 公告中把探索得到的激光对准过程固化为确定性程序，说明了这种分工。

## 03 · 协议名称与实现状态

| 名称 | 当前材料能支持的判断 | 适合借鉴的部分 |
| --- | --- | --- |
| **AIP** | 本次讨论的 Agent–Instrument Protocol PRD v1.1；是用户提供的设计参考，未核实对应公开实现。 | 常驻执行服务、类型化量与活动、设备类 profile、读数来源、资源关系和恢复语义。 |
| **LAP** | Lab Agent Protocol 的设计论文；论文明确没有规范性或已实现地位。 | InstrumentCard、预留、任务与测量结果的组合。 |
| **MCP** | 通用 Agent 工具协议，已有公开 SDK 与 Tasks 扩展。 | 工具发现、结构化参数、资源、能力协商和异步结果入口。 |
| **MHS** | Anthropic 的 Model Hardware Standard，仍以研究预览及申请入口对外展示；公告将开源放在后续阶段。 | 标准化驱动、设备发现、物理说明，以及 MCP / CLI / API 多种入口。 |
| **多个 Open-MHS** | 不同作者维护的社区工程；“受 MHS 启发”不等于官方实现或已验证兼容。 | 分别比较设备模型、适配器和真实运行记录。 |
| **OpenMHP** | 独立的公开规范与代码；设备包当前以模拟孪生验证为主。 | 精简工具面、按需描述、动作与任务、租约、方法包和结果记录。 |

[MHS 公告](https://www.anthropic.com/news/model-hardware-standard-research-preview) · [MHS 官网](https://modelhardwarestandard.com/) · [OpenMHP 规范](https://github.com/kushalsinha/openmhp/blob/main/SPEC.md) · [LAP 原文](https://arxiv.org/html/2606.03755v1) · [MCP Tasks](https://tasks.extensions.modelcontextprotocol.io/)

不能仅凭缩写推断机构归属。这里两个名为 MHP 的工程分别来自 kushalsinha 与 Cuntinum；AIP 也被多个身份、通信与工作流项目使用。目录按作者和完整仓库地址消歧。

MCP 可以通过 schema 表达单位、范围和设备字段，也已有异步任务扩展。仪器层需要补充的是这些字段的共同含义、设备端实现和可验证行为。仅增加字段不够；仅改用另一种传输也不够。

## 04 · 哪些工程值得优先深入

| 已有条件或研究问题 | 优先阅读 | 需要补齐的说明 |
| --- | --- | --- |
| 已有 QCoDeS 仪器和 Jupyter 测量 | instrMCP；QCoDeS | 实时值与缓存、持久任务、共享仪器的资源边界。 |
| 想研究可移植的设备描述和操作模型 | SiLA 2；LADS；WoT；OpenMHP；三个 Open-MHS | 同类设备的必选能力、可选功能与版本兼容。 |
| 大型设施已有 EPICS / TANGO / DOOCS | Osprey；TANGO MCP；EPICS MCP；VISION | 通道语义、设施上下文、计划执行与操作记录。 |
| 多设备实验和边缘执行 | PUDA；Uni-Lab-OS；IvoryOS | 拓扑、资源争用、样品流转、长任务恢复。 |
| 示波器、DAQ、电源与嵌入式开发 | LabLink；scope-mcp；Siglent MCP；DAQiFi；Embedded Debugger | 波形缩放、触发、采样时间、配置快照与固件信息。 |
| 显微镜、光机平台和视觉反馈 | OpenFlexure-MCP；microscope-agent；Agentic microscope；EAA 系列 | 图像与位置关联、曝光和校准、动作后的实际回读。 |
| 液体处理与化学机器人 | Opentrons MCP；plr-mcp；OpenLabAI；ChemAgents | 甲板与样品身份、单位、消耗量、移液操作与恢复边界。 |
| 量子与扫描探针实验 | LeeQ；NVIDIA QCA；Quailbot Pi；AILA | 校准状态、实验知识、反馈判断、外部驱动依赖。 |
| 软件只有 GUI | device-use；现有厂商自动化接口 | 界面版本、操作后验证、数据来源；先确认是否已有可用 SDK。 |

开源、实机验证和可直接部署是三个独立维度。MIT/Apache 项目可能只验证过模拟器；有真实实验论文的仓库可能只发布规划或分析代码。Coscientist 的 Commons Clause、LabscriptAI 的商业使用限制、Uni-Lab-OS 的框架与驱动许可分界，都会影响复用方式。许可证筛选与实验状态筛选因此分开。

判断生态地位时，优先看独立团队是否使用、覆盖哪些真实型号、设备制造商是否维护适配、说明是否版本化、有没有互操作测试。Stars、命名和一段演示不能替代这些证据。MHS 的机构协作值得关注，当前公开材料尚不足以据此认定一种通用仪器协议已经形成全球统一格局。

## 05 · 通用说明的最小内容

以下是本研究给 AI4Instruments 的设计建议，配套 JSON 是说明用草案。

| 对象 | 至少保留的信息 | 解决的具体问题 |
| --- | --- | --- |
| **Device / capability** | 稳定 ID、型号、驱动与固件、能力版本、可控与可观测量。 | 发现设备后知道能做什么，并识别版本变化。 |
| **Quantity / observation** | 值、单位、时间、来源、有效性；需要时附校准与不确定度。 | 分清设定值、实测值、缓存与推导值；不把 unknown 填成 0。 |
| **Operation** | 参数、前置条件、预期影响、可重复性、实际回读。 | 对网络超时后的物理结果作判断，避免盲目重发。 |
| **Job / activity** | 持久 ID、状态、进度、取消语义、终止原因、结果引用。 | 会话结束后仍能追踪实验；取消请求不冒充已停止。 |
| **Resource** | 实际共享对象、占用范围、互斥关系与冲突处理。 | 同一仪器的不同通道是否可并行，不只靠一把全局锁。 |
| **Event / record** | 单调序号、时间、因果关系、运行与设备 ID。 | 重连后还原发生过什么，并关联外部手动操作。 |
| **Artifact / dataset** | 内容引用、格式、校验、单位轴、采集配置与来源。 | 大数据不塞进工具文字；分析结果能追溯到原始采集。 |

设备类 profile 只规定确实可互换的核心能力，其余功能以可选能力和命名空间扩展。例如两个电源都能设置电压，不代表它们的斜坡、触发、保护状态和读回速度相同。通用性应建立在明确的共同部分上。

AIP 的丰富状态与活动模型值得借鉴，但实现成本也应落实到每个驱动：哪些状态能从硬件读到，哪些只能追踪，哪些根本无法确定。统一接口应保留这些差异，而不是让所有设备看起来拥有同样的可观测性。

长任务的持久性也不等于过程内存里有一个 task ID。需要明确进程退出后谁继续持有设备、记录如何落盘、重启后如何与设备实际状态对账。MCP task、运行器 job 和设备内部程序可以互相映射，但它们不是天然同一个生命周期。

## 06 · 三个具体实验

### 光学对准：观察必须跟得上动作

**Basic Operations**：读取光功率、采集相机帧、移动镜架或位移台，并返回单位、位置与时间。**Standard Operations**：在确定的扫描范围内移动、等待稳定、采样和拟合。**Workflow Operations**：标定坐标、寻找峰值、跟踪漂移、保存光路版本并比较下一次实验。

Agent 只提交优化目标与过程参数，本地程序负责扫描时序。功率必须与测量时的实际位置对应。电机收到移动命令后，若只有控制器回执而没有到位反馈，记录就应保留“已接受、位置未确认”。LabMCP 的光功率计组件可作接口参考，其当前模拟状态不会被写成实机验证。

### 长时间扫描：连接断开不应丢失实验身份

Agent 提交扫描计划，常驻执行层返回 job ID；程序拥有仪器连接和数据写入。界面重连后用同一 ID 读取事件及结果。若停止发生在第 47 点，记录保留前 46 点、当前点的真实完成状态和终止原因；不把部分数据解释为完整扫描。

这里需要分别定义通讯超时、执行失败和实验目标未达到。已发送但未收到响应的动作，先查状态与事件再决定下一步。网络重试策略不能直接决定是否重复物理操作。

### 液体处理：样品也是资源

从输入协议到机器人动作，需要明确液体、孔位、容器、吸头、体积和单位。工作流可以先由模拟器检查语法与路径，再交给机器人运行；真实液体性质、吸液高度和残留仍属于实验条件。

一次 dispense 响应丢失时，重复调用可能重复加液。应以机器人 run、事件和已完成步骤对账；这类动作不应仅凭 HTTP 请求重试机制获得“可靠性”。

## 07 · 从生态资料走向可复用工程

先选一个有明确物理回读的小型实验，复用已有驱动，把 Basic Operations 描述完整。接着将有效过程固化为可读、可执行的 Standard Operations，再由 Workflow Operations 组合。每一步保留实现与数据，使新的研究能够修改过程，而非只能调用固定黑箱。

| 阶段 | 交付物 | 可判断是否完成的证据 |
| --- | --- | --- |
| **设备说明** | 能力描述、量与观察、动作返回、版本规则。 | 两个型号使用同一核心 profile；差异由可选能力准确表达。 |
| **执行服务** | 连接所有权、长任务、事件与数据引用。 | 会话断开、程序重启、设备拒绝命令后，仍能解释真实状态。 |
| **过程复用** | 可读测量计划、可替换算法、数据与配置快照。 | 同一过程在不同 Agent 入口执行，原始记录保持一致。 |
| **生态协作** | 驱动模板、profile 注册、贡献规则、兼容性测试。 | 独立实验室可按文档接入，并提交带设备与固件信息的复现记录。 |

数据集需要同时保留失败、未知与部分完成的轨迹。它们能说明现有硬件缺少哪些回读、控制器需要哪些改变、哪些 Standard Operations 值得改进。这把 Instruments4AI 的接入工作连回 AI4Instruments 的仪器设计与持续开发。

## 08 · 阅读和维护这份资料

先读名称与分工，再按已有设备筛选目录。对入选项目依次查看接口、物理路径、实验状态、许可证和源码入口。最后比较它与实验室现有运行器之间缺少哪些映射。无需 fork 每个仓库；保留上游地址，只有实际修改和贡献时才建立工作分支或 fork。

项目目录、协议生态和设备组件分别存于 `catalogue.json`、`context.json`，网页内嵌同一份数据。`sources.json` 汇总来源；`catalogue.schema.json` 定义字段；`build.py` 使用 Python 标准库重建中英 HTML、目录和索引。两份 HTML 集成正文、目录、来源、字段规范和说明示例，可独立阅读、离线检索并导出内嵌资料；原始文档通过来源链接访问。

本次核查日期为 2026-10-20。收录依据是公开仓库、官方资料、论文和选定实现路径；实机状态引用作者或维护者的记录。组件和 fork 不重复计为独立工程。后续更新应记录具体的新增来源和状态变化，让这份资料继续可追溯地增长。
